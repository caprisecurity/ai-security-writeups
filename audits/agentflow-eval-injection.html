AgentFlow : eval injection via le tool-calling du LLM

Divulgation responsable · CWE-95 · Projet open source (PHclaw/agentflow)
Perimetre : revue de code statique uniquement
Aucune instance live/deployee touchee
Categorie
CWE-95
Vecteur reel
Injection de prompt
Chemins corriges
2
Statut
Corrige & credite
1 - La faille
Un outil "calculatrice" expose au LLM via function-calling (OpenAI-style tool-calling) evaluait directement l'expression recue avec eval(), sans aucun filtrage. Le vrai risque n'est pas qu'un utilisateur tape une expression malveillante a la main - c'est que n'importe quel texte que l'agent LIT (un message de chat, un document recupere, une page web dans un contexte RAG) peut convaincre le modele d'appeler l'outil "calculator" avec une expression piegee. Le modele n'a pas besoin d'etre "jailbreake" sur un sujet sensible - juste de croire qu'il fait un calcul banal, une barre bien plus basse qu'un refus de securite classique.
eval() direct sur l'argument "expression" du LLM
tools_memory.py::_calculator_tool - une expression comme "__import__('os').system(...)" donnait une execution de code arbitraire dans le processus backend.
Confirme
Second chemin vulnerable trouve par comparaison
Une 2e implementation "calculatrice" existait dans workflow_runtime.py, avec une liste blanche de caracteres qui bloquait __import__ mais pas les charges d'epuisement CPU (9**9**9**9). Signale et corrige dans le meme echange.
Confirme
2 - Comment Capri l'a trouvee
Pas un scan automatique de mots-cles dangereux (eval, exec) suffirait a trouver un eval() isole dans n'importe quel projet Python - ca ne prouve rien sur le risque reel. La vraie methode trace la CONFIANCE, pas la syntaxe :
1
Reperer ou le LLM pilote une action reelle
Chercher les points ou la sortie d'un modele (un nom d'outil choisi, des arguments remplis par le LLM) devient un appel de fonction reel cote serveur - pas juste du texte affiche a l'utilisateur.
2
Remonter la chaine jusqu'a la source de l'argument
L'argument "expression" vient du LLM, qui lui-meme construit sa reponse a partir de TOUT ce qu'il a lu dans la conversation - y compris du contenu que l'agent a recupere ailleurs (document, page web, message d'un tiers). Cette donnee, d'origine moins fiable que le code du developpeur, finit executee avec la meme confiance qu'une instruction du developpeur.
3
Comparer les chemins soeurs du meme projet
Une regle centrale de la methode : quand un projet a plusieurs implementations similaires (ici, deux "calculatrices"), comparer leur traitement du MEME type de donnee plutot que juger chaque fichier isolement. Un fichier correctement filtre a cote d'un fichier qui ne l'est pas est un signal de faille aussi fort qu'un pattern dangereux trouve dans un seul fichier - c'est exactement ce qui a revele le 2e chemin vulnerable ici.
3 - Reponse du mainteneur
Reproduit cote mainteneur, corrige par un parseur AST en liste blanche (constantes numeriques et operateurs arithmetiques uniquement, bornes sur l'exposant/l'operande/le nombre de noeuds), 42 tests de regression ajoutes, et credit public explicite a "Capri Security" dans le changelog du projet - divulgation close de bout en bout.
